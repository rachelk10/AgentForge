Stage Guide: Building the Client Side with Copilot
October 22, 2026 · Based on the Client-Side Specification, version 1.0 · English translation
1. Working Principles
• Save the specification in the repo as docs/client-spec.md. The prompts below refer to it by section number; the section numbers are identical in both language versions. The prompts are written in English so they can be pasted directly.
• For each stage: open a new Copilot chat, attach the specification file, and paste that stage's prompt.
• Plan before code: every prompt asks for a work plan and waits for your approval.
• At the end of each stage ask Copilot: "List every deviation from the spec and every assumption you made." Then review the list.
• Do not move to the next stage until the acceptance criteria are met and the tests pass.
• Stages 0–6 are already implemented in this project. Do not redo or change their stage prompts; use the interim stage after Stage 6 to complete missing real backend functionality for their existing user flows.
• Before Stage 9, decide whether changes after publishing take effect immediately or require "Publish". The prompt assumes "Publish" is required; change its wording if you decide otherwise.
2. Preparation: Permanent Instructions for Copilot
Create the file .github/copilot-instructions.md and paste the following into it. It applies to all stages.
Project: React + TypeScript (Vite) client for a no-code AI agent platform. Users are small business owners with no technical background. The full spec is in docs/client-spec.md; follow it and do not invent features outside it.

Rules:
- All user-facing text goes through react-i18next (he + en). No hard-coded strings.
- Support RTL and LTR. Use CSS logical properties (margin-inline-start etc.), never left/right.
- Copy is dignified and understated: no exclamation marks, no playful language, and no technical terms (prompt, schema, embeddings, tool JSON) shown to users.
- Accessibility: WCAG 2.1 AA, keyboard navigation, labels, sufficient contrast.
- Forms: react-hook-form + zod. Server state: TanStack Query. Types generated from the backend OpenAPI schema.
- Every data view handles loading (skeletons), empty and error states.
- The existing developer panel (App.jsx) must not be modified or exposed to business owners.
- For the interim stage after Stage 6 and all subsequent stages, keep API types synchronized with backend OpenAPI and implement missing endpoints in the backend rather than mocking them in the running application. MSW may be used for isolated tests, not to simulate completed product functionality.
- Before writing code for a task, outline a plan and wait for approval. Keep changes scoped to the task.
3. Stage 0: Infrastructure
Spec sections: 3, 9, 10.
Read docs/client-spec.md sections 3, 9 and 10. Task: set up the client infrastructure only, with no product screens.
- Vite + React + TypeScript structure, React Router, and an app shell.
- i18n with he and en, a language switcher, and automatic dir (rtl/ltr) on <html>.
- API client generated from the FastAPI OpenAPI schema (openapi-typescript), a TanStack Query provider, and an auth-aware fetch wrapper.
- MSW configured for development and tests.
- Base accessible, RTL-safe components: button, input, card, dialog, toast, skeleton.
- A route guard for authenticated routes. Keep the existing App.jsx developer panel on a separate /admin route restricted to the admin role.
First outline a plan and wait for my approval.
Acceptance criteria: the app runs; switching language flips the direction; types are generated from OpenAPI; the base components have tests; the developer interface sits on a separate route.
4. Stage 1: Registration and Login
Spec sections: 4, 5.1.
Read docs/client-spec.md sections 4 and 5.1. Task: build registration and login.
- One screen with Register and Log in tabs, plus a "Continue with Google" button. Fields and validation as in 5.1, with human-readable error messages.
- Use the existing backend auth endpoints from the OpenAPI types. Google sign-in and password recovery do not exist yet: define contracts and mock them with MSW.
- Keep token storage behind a small auth-storage module so the method (memory vs httpOnly cookie) can change later.
- Post-login redirect per section 4, using a contract for the user's agent state: none | draft | published.
- Language selector visible on every screen, including before login.
First outline a plan and wait for my approval.
Acceptance criteria: registration and login work against the existing backend; the redirect by agent state is correct; error messages are worded in a human way; the screen works in both languages.

First outline a plan and wait for my approval.

7. Stage 4: Wizard Step 3 (Capabilities)
Spec sections: 5.3 (Step 3), 7.
Read docs/client-spec.md sections 5.3 (Step 3) and 7. Task: build wizard Step 3 (Capabilities), driven entirely by a backend catalog.
- Define a catalog contract, for example {id, name, description, default_enabled, locked, config_fields[]}, and mock it with: lead collection, meeting scheduling, handoff to a representative, plus one locked capability.
- Capability cards with an on/off switch and a Configure button. No capability is hard-coded in the UI.
- Build a generic form renderer from config_fields (text, email, number, multi-select, a list editor for lead fields, and a weekly availability editor for days and hours). Forms are worded in business language.
- Locked capabilities show a lock and "Available in an advanced plan" and cannot be toggled.
- A "Ready-made behaviors" (Skills) picker: choose from a list with name and description, no free-form editing.
- Never display technical names, schemas or identifiers.
First outline a plan and wait for my approval.
Acceptance criteria: adding a new capability to the mocked catalog makes it appear on screen with no code change; the form is built from the field definitions; locked capabilities cannot be enabled.

First outline a plan and wait for my approval.

9. Stage 6: Widget and Standalone Chat Page
Spec sections: 5.5, 9 (performance and security), 10.
Read docs/client-spec.md sections 5.5, 9 and 10. Task: build the embeddable widget and the standalone chat page.
- A separate package (packages/widget): a short loader script that injects an isolated iframe, and the chat UI inside it. Target size: up to 50KB gzipped.
- Behavior per 5.5: floating button (side follows writing direction), full screen on mobile, logo, agent name, opening message, language detection from host page or browser, automatic text direction per message, typing indicator, and retryable errors.
- In-chat flows: lead collection with a confirmation message, meeting slots as selection buttons, handoff message with a contact-preference question, an automated-reply note, and a paused-agent state.
- Standalone page at /chat/:publicKey with the same look and behavior.
- Public endpoints use a public key, not the owner's auth. Define the contracts and mock them. Sanitize all rendered message content.
First outline a plan and wait for my approval.
Acceptance criteria: the widget loads on a test page without disturbing the host site; the package size is within the target; it works properly on mobile and in both languages; message content is sanitized.

Interim Stage (after Stage 6): Complete the Real Backend for Stages 0–6
This additional stage is for a project whose frontend Stages 0–6 are already implemented. Do not redo or redesign those stages. Preserve their existing screens and behavior; make only the necessary backend and API integration changes to make the existing in-scope flows real.
Read docs/client-spec.md sections 1, 2, 5, 6, 8, 9, 11 and 14. Task: make every in-scope feature already presented by Stages 0–6 work through real backend endpoints and persistent data.
- Audit the completed frontend's API calls/contracts and MSW handlers against the actual FastAPI OpenAPI schema and the dependency checklist in section 11. Map each in-scope feature to its real endpoint and persisted data.
- Implement missing backend endpoints and supporting schemas, services, database models/migrations, validation, ownership/authorization, and tests. Regenerate frontend API types from OpenAPI and wire the existing screens to these real endpoints.
- Complete the real flows represented in Stages 0–6: agent state and draft autosave/resume; template catalog and applying a template; free-text information sources and website scanning with real processing statuses/retry; capability and ready-made behavior catalogs/configuration; generated agent instructions; test conversations marked and excluded from business data; logo upload; publication and public key; widget and standalone chat APIs; real message processing; and lead collection, meeting availability/booking, and handoff request creation where offered by the existing UI.
- Implement Google sign-in and password recovery with actual provider-backed flows and required configuration if those controls are present in the completed UI. Do not report these as working unless the real provider flow is configured and verified.
- Remove MSW from application runtime paths for these in-scope features. MSW and test fakes may remain only in isolated frontend tests. Do not use hard-coded fixtures, seeded success responses, local-only storage, or fake provider responses as substitutes for backend functionality.
- Preserve the existing UI and the specification's out-of-scope decisions. Do not add Google Calendar, payment, external channels, live human chat, or other future extensions.
- Document required environment variables and provider setup. Missing configuration must produce an explicit actionable error; never silently claim a real operation succeeded.
First outline a plan and wait for my approval.
Acceptance criteria: the already implemented Stages 0–6 work against the real backend with application MSW disabled; drafts and created data persist across reloads; real chat-created conversations and enabled business actions are stored and retrievable; backend tests cover validation and ownership; frontend integration tests verify real API wiring; provider-dependent flows are verified with configured test providers or explicitly reported as blocked rather than working.

11. Stage 8: Leads, Meetings, and Pending Requests
Spec sections: 5.4 (Leads, Meetings, Pending requests).
Read docs/client-spec.md section 5.4 (Leads, Meetings, Pending requests). Task: build these three pages.
- Implement or complete the real backend APIs and persistence for leads, meetings, and handoff requests, then wire the pages to those APIs. Enforce agent ownership and exclude test data from business lists.
- Leads: a table of actually collected fields, date, link to the conversation and persisted status (new, handled); CSV export.
- Meetings: list real bookings created through the agent's configured availability, with a persisted cancel action and a confirmation dialog. Use the in-product availability model; Google Calendar integration is out of scope.
- Pending requests: persisted customer details, handoff reason, time, link to the conversation, a saved "Handled" status and internal note. Send the specified email notification through the configured email provider; do not simulate successful delivery.
- Handle loading, empty and error states on every page. Do not use mock handlers or fabricated data in the running app.
First outline a plan and wait for my approval.
Acceptance criteria: a lead, booking, and handoff request created through a real chat are visible with their actual data; CSV export works in Hebrew and English; handled status and notes persist; cancelling a meeting requires confirmation and is persisted; the notification is verifiably delivered in the configured test mailbox/provider; tests cover ownership and error cases.
12. Stage 9: My Agent and Pausing
Spec sections: 5.4 (My agent, Paused agent), 13.
Read docs/client-spec.md section 5.4 (My agent, Paused agent). Task: build the My agent area and pause/resume.
- Reuse the wizard step components as separate edit pages: business, information, capabilities, appearance, embedding.
- Decision for this task: changes made after publishing are saved as a draft and take effect only when the owner presses "Publish". Show an unsaved/unpublished changes indicator and a leave warning.
- Pause/resume with confirmation and a persisted backend state. While paused, the public widget and chat page must read that state from the real public API and immediately show the unavailable message.
- Keep draft settings separate from published settings. Publishing must persist and atomically activate the saved version; verify that the widget and standalone page use the published version and that a pause takes effect without republishing.
First outline a plan and wait for my approval.
Acceptance criteria: there is no code duplication between the wizard and edit pages; edits, publication, and pause/resume persist across reloads; unpublished changes are marked and do not leak to public clients; publishing updates the public widget; pausing affects the widget and chat page immediately.
13. Stage 10: Polish and Edge-Case Testing
Spec sections: 3, 8, 9.
Read docs/client-spec.md sections 3, 8 and 9. Task: quality pass across the whole client.
- First audit every frontend API call, contract, and MSW handler. For each in-scope feature in the specification, verify that the application uses a real backend endpoint and persisted state; implement any remaining backend work. There must be no mocked production path or fake success response for an in-scope feature.
- Playwright end-to-end flow against the real FastAPI backend and persistent integration database: register/log in, choose a template, complete the wizard with real information sources and capabilities, test, publish, embed the widget on a sample page, send a message through the configured agent runtime, and see the persisted conversation in the dashboard. Run it in Hebrew (RTL) and English (LTR), with MSW disabled.
- Verify real lead submission, meeting booking/cancellation, handoff request and email notification, logo upload, pause/resume, published-versus-draft behavior, and session-expiry draft restoration. Use safe test accounts and configured test services; do not substitute mocks to make the flow pass.
- Automated accessibility checks (axe) on every screen, plus keyboard-navigation checks on the wizard and widget.
- A copy review: find strings that contain exclamation marks or technical terms from the forbidden list, and any hard-coded text outside translation files.
- Check loading, empty and error states on every data view, and session-expiry draft restoration.
- Run backend and frontend regression tests, including API authorization/ownership checks and migrations. Verify that API errors are surfaced to the user and that no feature reports success when its operation failed.
- Report the verification environment and external services used, the real end-to-end results, and any remaining blockers or required configuration. List any remaining mocks only if they are confined to isolated tests or explicitly out-of-scope future extensions; none may remain on an in-scope application path.
First outline a plan and wait for my approval.
Acceptance criteria: the full flow passes in both languages against the real backend and configured integrations with MSW disabled; in-scope data survives reloads; there are no accessibility findings; every in-scope API call uses a real implementation, and any unverified provider or configuration dependency is reported as a blocker rather than presented as working.
